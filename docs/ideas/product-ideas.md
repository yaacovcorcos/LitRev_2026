# Product Ideas

This file is a staging area for rough product ideas before they are promoted into canonical plans or implementation work.

Every new idea added here must first be reviewed against the existing file to determine whether it:
- fits an existing topic section,
- should extend or merge into an existing idea,
- duplicates something already captured,
- or requires the file structure itself to be reorganized before the idea is added.

Default rule: prefer updating the right existing section or idea rather than creating a new standalone entry.

## Status Legend
- idea: raw concept, not yet shaped
- exploring: under discussion
- ready: clear enough to move into a plan
- rejected: intentionally not moving forward

## Top Priority

## Citations and References

### Inline Citations and Reference Lists in Draft + Chat
- Status: exploring
- Summary: Both the draft experience and chat experience need first-class support for inline citations and a generated reference list at the end.
- Why this matters:
  - This is one of the most important product gaps right now.
  - Users need output that is much closer to usable academic writing.
  - Citations and references need to work consistently across drafting and conversational writing flows.
- Draft requirements:
  - Insert inline citations directly into generated or rewritten draft text.
  - Maintain or generate a references section at the end of the draft or section output.
  - Keep citation formatting tied to real studies in the project ledger.
- Chat requirements:
  - Allow chat responses to include inline citations in the body text.
  - Allow longer writing-style chat responses to include a references list at the end.
  - Make cited studies traceable and grounded to actual project sources.
- Open questions:
  - Which citation style should be supported first
  - Whether references should be appended automatically or optionally
  - How inline citations map to ledger studies and draft rich-text structure
  - Whether chat references are per-message only or can be saved into draft artifacts

### Citation Architecture Direction
- Status: exploring
- Summary: Citations should be treated as structured app-owned references shared by draft and chat, not as freeform formatted text produced directly by the model.
- Current state:
  - Draft already has structural citation handling and generated references.
  - Chat still relies too much on prompt conventions and link-style citation behavior.
  - The main gap is the lack of one shared citation contract across surfaces.
- Direction:
  - Keep `studyId` as the canonical evidence anchor.
  - Add a CSL-JSON-compatible projection for ledger studies.
  - Let the model emit citation intent, while the app owns inline citation rendering and reference-list generation.
  - Converge draft, chat, and export on one shared citation layer.
- Strong references:
  - `Citation.js` for rendering and metadata normalization
  - `CSL` for style/schema standards
  - `Manubot`, `Curvenote`, `JupyterLab Citation Manager`, `PaperQA`, and `LARS` for product and architecture patterns
- Things to avoid:
  - Letting the model free-write canonical references
  - Keeping separate citation semantics in chat and draft
  - Treating DOI links alone as the citation model

## Onboarding and Entry

### Reduce the Number of Questions at Project Start
- Status: exploring
- Summary: The beginning of a project currently asks for too much too early, and the setup flow should feel lighter and more progressive.
- Why this matters:
  - Too many questions upfront create friction before the user has momentum.
  - Early uncertainty is normal, especially before the user has explored the literature.
  - The product should help users start quickly and refine later rather than forcing premature specificity.
- Direction:
  - Reduce the amount of required input at the very beginning of a project.
  - Shift more questions into later guided refinement after the user has context.
  - Distinguish clearly between what is essential to start and what can wait.
- Open questions:
  - Which setup questions are actually required for project creation
  - Which questions should be deferred until after scoping or early search
  - How much structure should be generated by default vs requested explicitly

### Make Onboarding Dynamic
- Status: exploring
- Summary: Onboarding should adapt to the user's progress and certainty instead of forcing the same fixed setup flow for every project.
- Why this matters:
  - Different users arrive with very different levels of clarity, materials, and readiness.
  - A rigid onboarding flow creates unnecessary friction and can ask the wrong questions at the wrong time.
  - The app should progressively guide users based on what they already know and what has already been inferred.
- Direction:
  - Make onboarding conditional on project state, available inputs, and user confidence.
  - Use earlier answers and existing artifacts to reduce redundant questions.
  - Let the setup flow expand only when deeper structure is actually needed.
- Open questions:
  - Which signals should control onboarding depth and branching
  - What the minimum viable onboarding path should be
  - When the app should infer defaults versus explicitly asking
  - How to let users revisit and deepen setup later without friction

### Open New Projects Directly in AI with a Clear Path to Projects
- Status: exploring
- Summary: Consider opening the app directly on the AI page by default, while keeping a very clear and simple click path to the projects page.
- Why this matters:
  - The AI page may be the fastest way to create momentum and make the app feel immediately useful.
  - New users can start interacting before they fully understand the broader project structure.
  - The projects page still needs to remain obvious and easy to reach for navigation and management.
- Direction:
  - Evaluate making the AI page the default landing surface when entering the app.
  - Add a clear, low-friction navigation action to reach the projects page.
  - Keep the entry flow simple enough that users do not get lost between chat-first and project-management workflows.
- Open questions:
  - Whether this should apply only to new users or to all users
  - What label and placement make the projects entry point most obvious
  - Whether the AI landing page should adapt based on whether projects already exist
  - How this choice affects onboarding, memory, and project creation flows

## Memory and Protocol

### Fix the Boundary Between Memory Updates and Protocol Updates
- Status: exploring
- Summary: The app needs a clearer rule for when information should update memory versus when it should update the protocol.
- Why this matters:
  - The current behavior can mix durable preferences and workflow habits with project methodology decisions.
  - Users should be able to trust where a change will live and what it will affect.
  - Protocol changes and memory changes have different meanings, scopes, and review expectations.
- Direction:
  - Clarify the contract for what belongs in memory and what belongs in protocol.
  - Make the system more consistent about when each store is updated.
  - Reduce confusion when the app interprets a user statement as a lasting preference versus a project-specific methodological decision.
- Open questions:
  - Which kinds of statements should always map to protocol
  - Which kinds of statements should always map to memory
  - When the app should ask before writing to one or the other
  - How conflicts between remembered preferences and protocol state should be surfaced

## Ledger and Study Intake

### Make Ledger Duplicate Detection Identifier-First
- Status: exploring
- Summary: When adding a study to the ledger, duplicate detection should rely primarily on stable identifiers like DOI and PMID rather than only the study title or name.
- Why this matters:
  - Title-based matching is too weak and can create false duplicates or missed duplicates.
  - Scientific studies often have title variants, punctuation differences, abbreviations, or partial metadata.
  - Ledger integrity depends on matching against the most specific identifiers available.
- Direction:
  - Prefer DOI, PMID, and similarly strong identifiers when deciding whether a study already exists in the ledger.
  - Treat title or name matching as a weaker fallback rather than the main deduplication rule.
  - Make duplicate handling more trustworthy when studies are added from chat, search, PDF extraction, or manual entry.
- Open questions:
  - Which identifier types should be considered canonical for duplicate detection
  - What the fallback order should be when DOI or PMID is missing
  - How to surface “possible duplicate” versus “confirmed duplicate”
  - How merged or corrected identifiers should rewrite existing references in draft and chat

## Draft and Writing

### Draft Rewrite Modes
- Status: exploring
- Summary: Add two rewrite options in the draft experience.
- Quick rewrite:
  - Faster rewrite path.
  - Uses limited context.
  - Intended for lightweight local improvement.
- Intelligent rewrite:
  - Higher-quality rewrite path.
  - Uses broader context.
  - Agentic, multi-step, can check protocol and other draft sections before rewriting.
- Open questions:
  - Final naming
  - Exact context included in each mode
  - UX entry points
  - Expected latency
  - Whether output is direct replace, proposal diff, or both

## PDF and Document Understanding

### PDF Parsing Reorganization
- Status: exploring
- Summary: Reorganize the PDF parsing pipeline to improve quality, structure, and depth across both parsing phases.
- Goals:
  - Make the parsing flow more organized and easier to reason about.
  - Improve the quality and usefulness of the fast first-pass extraction.
  - Expand the deeper second-pass analysis to produce richer insights.
- Phase 1 direction:
  - Optimize the quick pass for better extraction quality and cleaner structure.
  - Improve what is captured early so the system starts from a stronger baseline.
- Phase 2 direction:
  - Make the deeper pass substantially more insightful.
  - Extract more meaningful structure, interpretation, and downstream-usable signals.
- Open questions:
  - What exact outputs each phase should produce
  - Whether phase 1 and phase 2 should share a common intermediate representation
  - Which insights are most valuable for later search, screening, drafting, and QA flows
  - What should be stored vs computed on demand
