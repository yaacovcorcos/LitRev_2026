# Deep Review Template

Review date: 2026-03-21
Reviewer: Codex
Scope: Lint governance and agent-enforceable architecture constraints
Comparison baseline: `docs/reviews/repo-health.md`

## Executive Summary

- Linting is not currently a reliable merge gate because CI does not run `npm run lint`, while the local lint baseline is already deeply red.
- The repo has strong architectural intent in `AGENTS.md`, but most of that intent is not yet encoded as machine-checkable rules for agents.
- The highest-value first wave is not style polish. It is codifying deterministic imports/exports, effect discipline, structured error/logging conventions, and colocated test expectations.

## Findings

- Severity: High
  Title: Lint is not a trustworthy enforcement surface yet
  Why it matters: The repo cannot use "lint green" as a definition of done while CI skips lint and the current baseline contains hundreds of failures. Agents will not reliably self-correct against rules that are not on the hot path.
  Evidence with file references:
  - `.github/workflows/ci.yml` runs typecheck, governance checks, tests, and build, but not `npm run lint`.
  - `next-app/package.json` defines `"lint": "eslint && npm run check:theme-primitives"`.
  - `npm run lint` on 2026-03-21 reported `523 errors` and `591 warnings`.
  Whether it is new, recurring, or a regression: New documented finding.
  Required fix or containment: Restore a clean or intentionally-waived lint baseline, then add lint to CI as a required check.

- Severity: High
  Title: Repo-wide architectural rules mostly live in prose, not executable rules
  Why it matters: `AGENTS.md` contains specific repo contracts for effect discipline, route-shell behavior, styling tokens, and layer boundaries, but `next-app/eslint.config.mjs` currently contains only one narrow warning-only import restriction plus the default Next/TS config.
  Evidence with file references:
  - `AGENTS.md` declares strict UI delivery and effect-discipline rules.
  - `next-app/eslint.config.mjs` only adds a warning-only `no-restricted-imports` rule for four files.
  - `next-app/scripts/check-chat-stream-architecture.mjs` shows the repo already relies on custom executable architecture guards, but that pattern has not been generalized.
  Whether it is new, recurring, or a regression: New documented finding.
  Required fix or containment: Map major governance rules to Rule IDs and implement them as ESLint rules or guard scripts, starting with the highest-risk recurring patterns.

- Severity: High
  Title: Effect-driven orchestration is a recurring hotspot in client runtime code
  Why it matters: The repo explicitly treats direct effects as an exception, yet core client surfaces still depend heavily on `useEffect`, exhaustive-deps waivers, and state-setting effects. This is exactly the kind of drift agents will keep reproducing unless it is mechanically blocked.
  Evidence with file references:
  - `next-app/contexts/ProjectCopilotContext.tsx` imports `useEffect` and contains many effect-driven flows plus an `exhaustive-deps` suppression.
  - `next-app/app/project/[id]/layout.tsx` imports `useEffect` and coordinates shell runtime behavior through multiple effects.
  - `next-app/app/HomeClient.tsx` imports `useEffect` and contains hydration/performance effects.
  - `npm run lint` reports `react-hooks/set-state-in-effect` failures in `next-app/app/project/[id]/draft/AddEvidenceModal.tsx` and `next-app/app/project/[id]/draft/page.tsx`.
  - `rg` found multiple `react-hooks/exhaustive-deps` suppressions in `next-app/hooks/useCopilotConversations.ts`, `next-app/hooks/useCopilotStreamActions.ts`, `next-app/components/copilot/CopilotInputCore.tsx`, `next-app/contexts/ProjectCopilotContext.tsx`, and `next-app/app/project/[id]/draft/useDraftSections.ts`.
  Whether it is new, recurring, or a regression: Recurring pattern.
  Required fix or containment: Expand effect-discipline rules beyond the current hot-spot warning, then refactor the heaviest controllers toward reducer/controller/shared-hook ownership before escalating rule severity.

- Severity: Medium
  Title: Import and export conventions are not deterministic enough for agent searchability
  Why it matters: Predictable imports/exports are the lowest-cost way to make the repo easier for agents to search, place, and refactor safely.
  Evidence with file references:
  - `next-app/app/HomeClient.tsx`, `next-app/app/project/[id]/ProjectDetailClient.tsx`, and `next-app/app/project/[id]/onboarding/ProjectOnboardingClient.tsx` use non-framework default exports.
  - `next-app/components/project/ConversationMainView.tsx` mixes `@/` imports with relative cross-folder imports such as `../copilot/TimelineRenderer` and `../ui/ConversationPicker`.
  - `rg` found 58 non-test parent-directory imports (`../`) across `app`, `components`, `contexts`, `hooks`, and `lib`.
  Whether it is new, recurring, or a regression: Recurring pattern.
  Required fix or containment: Ban default exports outside framework-required files and ban parent-directory relative imports across feature/module boundaries in favor of `@/` paths.

- Severity: Medium
  Title: Logging and error semantics are inconsistent across client and server surfaces
  Why it matters: The codebase already has structured result/error patterns, but raw `console.error` and `catch(console.error)` remain widespread. This makes telemetry less consistent and teaches agents to add ad hoc logging instead of using sanctioned pathways.
  Evidence with file references:
  - `next-app/lib/server/action-utils.ts` centralizes `ActionResult` and sanitization but still logs with raw `console.error`.
  - `next-app/contexts/LedgerContext.tsx`, `next-app/components/markdown/CodeBlock.tsx`, and many runtime files use `.catch(console.error)` or ad hoc `console.error(...)`.
  - `rg` found widespread raw console usage across client code, server runtime code, and actions.
  Whether it is new, recurring, or a regression: Recurring pattern.
  Required fix or containment: Define allowed logging surfaces by layer, ban `catch(console.error)`, and require structured metadata for server/runtime logging paths.

- Severity: Medium
  Title: Test coverage is broad, but test placement policy is not yet deterministic
  Why it matters: The repo has many tests, but agents cannot infer a stable one-to-one placement rule from the current structure. That reduces the likelihood they add the right test automatically.
  Evidence with file references:
  - `find` counted 446 non-generated TS/TSX source files under `app`, `components`, `contexts`, `hooks`, and `lib`, and 283 test files.
  - `next-app/app/actions` contains 20 action modules, but `next-app/app/actions/__tests__` contains only 2 tests.
  - `next-app/lib/server/__tests__` is comprehensive, but many tests are centralized rather than predictably colocated with the source file they protect.
  Whether it is new, recurring, or a regression: New documented finding.
  Required fix or containment: Start with a narrow colocated-test rule for new files in selected domains instead of trying to retrofit the whole repo in one pass.
